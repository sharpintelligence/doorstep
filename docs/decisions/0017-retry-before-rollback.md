# 0017: Retry before rollback

- Status: Proposed
- Date: 2026-11-24

## Context

Many self-hosted clusters run on old or consumer hardware. A deploy can fail there for reasons unrelated to the new version: a slow or flaky node, an image pull that times out, a pod killed for memory on a small machine, a pod scheduled onto a node that then drops. Until now the engine failed a deployment the first time Argo CD did not report it synced and healthy within `argocd.sync_timeout`, so a good release was thrown away, and once automatic rollback (doorstep-ehl.6.2) exists it would be rolled back, on every such hiccup.

Constraints: doorstep never writes to the cluster and holds no Argo CD token ([ADR 0001](0001-go-and-core-design.md), decision 2); the only thing it writes is git, through pin commits whose trailers are the deploy history in the GitOps repository ([ADR 0005](0005-pin-commits-and-trailers.md)); the engine owns retry policy and routes every failure through one `FailurePolicy` hook ([ADR 0012](0012-deployment-engine.md), decision 5); [ADR 0002](0002-rollback-is-a-new-deployment.md) makes a person's re-run of a failed deployment a deployment of its own (`parent_id`); [ADR 0008](0008-kubernetes-rest-client.md) asks that every new Kubernetes resource doorstep reads be recorded in an ADR. Bead 7.2 (the web UI) is built at the same time, so new states would ripple into work in progress.

## Decision

1. **A retry is a fresh observation window on the same pin.** No new deployment row, no new digest, no new pin commit and no write to the cluster. The engine records a `syncing → syncing` transition (one per extra attempt), releases its claim for a backoff, and then waits the full `argocd.sync_timeout` again for Kubernetes and Argo CD to converge: reschedule, re-pull, restart. Kubernetes keeps retrying pulls, scheduling and restarts on its own; what threw good releases away was doorstep giving up at the first timeout.
2. **Attempts stay inside one deployment.** Automatic attempts are transition events of the deployment that failed. `parent_id` stays reserved for a person re-running a failed deployment.
3. **The state is derived from events, with no new state and no migration.** `core` allows the self-transition `syncing → syncing`. Its event data is `{stage, failure_class, sync_reason, retry: {attempt, next_attempt, max_attempts, delay_ms, reason, summary}, diagnosis}`. `store.TimeInState` already measures from the newest transition into a state, so the deadline restarts; `store.RetryState` counts the events carrying `retry` and returns the newest `delay_ms` and `max_attempts`. The sync step measures each attempt's window from the end of the pause (`TimeInState(syncing) − delay`) and releases again for the remainder when a claim arrives early, so the pause survives a restart.
4. **Only Argo CD wait failures in `syncing` are retried**, for deploys and rollbacks alike. Failures in `queued`, `resolving` and `pinning` keep their time-bounded handling; after-gate failures in `verifying` are final and count as version-caused. The engine fails a deployment when a policy asks to retry anything else.
5. **The policy owns judgement, the engine owns mechanics.** `FailurePolicy.Decide(ctx, Failure) (Decision, error)` returns an action (`fail` or `retry`), a typed `DecisionReason` (`transient`, `version_caused`, `retries_exhausted`, `not_retryable`, `retries_disabled`, `newer_release_queued`), a class, a one-line summary, a delay, the attempt budget and an opaque JSON diagnosis. `Failure.Attempt` is 1-based and filled by the engine. The engine counts attempts, records the transition, waits, notifies and counts metrics; `engine` still imports only `core` and the standard library.
6. **A classifier in a new package, `internal/retry`.** It imports `core` and `engine` and holds a pure `Classify` and the `Policy`. In order: a failure that is not an Argo CD wait failure keeps the engine's class; `not_found`, `forbidden`, `untracked_revision` and out of sync with manual sync are configuration; `sync_failed` (failing hooks, migrations) is the version; pod signals come next, with unschedulable, image pull errors, a lost node, eviction, containers stuck creating and running-but-not-ready leaning transient, `InvalidImageName` and `RunContainerError` blaming the version, and crash loops and OOM kills decided by evidence; without signals, `degraded` is downgraded to unknown and other reasons keep their class. Transient and unknown failures are retried while attempts remain. Classification always runs, so the diagnosis is recorded even when retries are off.
7. **Evidence decides crash loops and OOM kills**, in order: (a) a pod of the previous digest is unhealthy on the same node, or the node appears in the diagnoses of another digest of this target in the last 7 days, so the hardware is at fault; (b) the same termination reason and exit code on two or more distinct nodes, in this attempt or an earlier one of this deployment, so the version is; (c) a previous-digest pod is ready on the same node, so the version is; (d) otherwise unknown, which is retried. New and previous pods are told apart by the `@<digest>` suffix of their images.
8. **Pod reads are opt-in and read-only.** `kubernetes.pod_diagnostics` (default off) lets doorstep list pods: `argocd.Watcher.Workloads` reads the Deployments, StatefulSets, DaemonSets and Rollouts from the Application's `status.resources`, and `internal/pods` lists pods with one `GET /api/v1/namespaces/{ns}/pods?limit=500` per namespace (at most five) and matches them by controller owner reference. Only the fields the classifier needs are decoded, so environment values are never held or logged. A `403` or any other read error degrades to classification from the Application alone. The optional kustomize component `components/pod-diagnostics` grants `list` on `pods` and sets the flag; the base keeps its `applications`-only grant. ADR 0001's list of what doorstep reads gains "`list` on core `pods`, opt-in".
9. **A waiting deployment is not held back.** Before retrying, the policy reads the target's queue; when another deployment is waiting, it fails with `newer_release_queued` instead. Rollback requests already cancel the active deployment.
10. **Per-app configuration with retry-first defaults.** `apps[].retry: {enabled: true, max_attempts: 3, backoff: 1m, max_backoff: 10m}`; `max_attempts` counts every attempt including the first (1 to 10), `backoff` doubles per attempt from 0 to 1 hour, `max_backoff` is at least `backoff` and at most 6 hours, with no jitter. An omitted block means the defaults.
11. **One new notification kind.** `deploy.retrying` is sent on the first failed attempt only and is on by default. The final decision rides on the existing terminal kinds with a message: `deploy.failed` (version-caused, or still failing after the budget) and `deploy.succeeded`/`deploy.rolled_back` (succeeded on attempt N of M). GitHub deployment statuses ignore `deploy.retrying`.
12. **The failure event marks rollback eligibility.** The `failed` transition's data gains `attempts`, `decision`, `rollback_eligible` and `diagnosis`. A failure is eligible when it is a deploy that failed in `syncing` or `verifying` with a pin, and its decision is `version_caused` or `retries_exhausted` (an after-gate failure of class `version` counts as version-caused). Configuration failures and `newer_release_queued` are not eligible. Manual rollback stays available regardless.
13. **One metric.** `doorstep_deployment_retries_total{app, class}`; duration and outcome metrics are still recorded once, at the terminal transition.

## Options considered

- **Nudge Argo CD with a git commit per retry (an empty commit, or an annotation bump).** Rejected. An empty commit does not restart pods; it only un-sticks `sync_failed`, which is version-caused anyway (failing hooks and migrations). An annotation bump needs doorstep to understand the manifests, adds a pull request per retry in `pull_request` mode, pollutes the pin history and its trailers (ADR 0005), and restarts healthy replicas on a node that is already struggling. Waiting changes neither the security model nor the git history.
- **A child deployment per attempt, linked by `parent_id`.** Rejected. Every attempt would emit `deploy.failed`, run the before gates, resolve and pin again, trip duplicate detection and look like a failed release to automatic rollback. One deployment per release keeps history, notifications and the one-active-deployment-per-target invariant honest.
- **A `retrying` state, or a column for the attempt count.** Rejected. A state touches the database check constraints, the active-state index, the API, the UI being built in parallel, metrics, rollback cancellation and notifications. A column duplicates what the events already hold, and the event log is already the source of truth for deadlines on the database clock.
- **Retrying after-gate failures.** Rejected for now. Gates carry their own patience (health gate timeout, Prometheus thresholds) and sticky verdicts; retrying them needs a `verifying → syncing` path and one-shot re-evaluation bookkeeping, which [rollback.md](../rollback.md) deliberately avoids. Metric, external and Job gate failures are version-caused by definition.
- **Classifying from the Application only.** Rejected as the only source: Argo CD's Application carries no pods, and Argo CD 3 no longer persists resource health in it, so the node evidence the bead asks for needs pod reads. It remains the fallback, by keyword, when pod reads are off or fail.
- **Watching pods, or reading events and logs.** Rejected. One list per namespace at the moment of failure is enough, needs one verb on one resource, and keeps doorstep stateless.
- **Jitter in the backoff.** Rejected: one target retries alone, so jitter spreads nothing and makes the worst case harder to state and to test.
- **A separate "final decision" notification kind.** Rejected: the terminal kinds already are the final decision, and a parallel kind would notify every channel twice.

## Consequences

- A slow node, a flaky pull or an OOM on a small machine costs a retry, not a release. With the defaults, the worst case before a deploy fails is three windows plus two pauses: 3 × 10m + 1m + 2m = 33 minutes. Pauses release the claim, but each window holds one of the replica's `engine.concurrency` slots.
- A version that crash-loops on several nodes, fails its sync hooks or cannot start its image fails at once instead of after three windows.
- On a single-node homelab, evidence (a) can blame the hardware for a version that broke twice in a week; the attempt budget bounds the cost.
- Deployment history shows each attempt, its reason and its diagnosis, and automatic rollback (doorstep-ehl.6.2) can act on `decision` and `rollback_eligible` without parsing text.
- Installations that want node evidence must apply the `pod-diagnostics` component, which widens the RBAC footprint from Applications to listing pods cluster-wide (or per namespace with a RoleBinding).
